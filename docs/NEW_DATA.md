**Доступность: ДА (открыто, без ключа) — проверено живыми запросами 20.09.2026:**

| `GET /api/calendar/towns` | **200, 290 КБ** — `{"success","result":{"count","entities"}}`, **400 станций/пунктов**, ~38 совпадений «Акмол…» (имена в кириллице, консоль их исказила, но счётчик совпадений снят кодом) |

**Формат:** JSON `{success, result}` (списки — `{count, entities}`), даты ISO, имена RU/KK. Прогноз засухи — через стандартизированный индекс осадков (СИО: норма −0.99…0.99, умеренная/сильная/экстремальная засуха), влага — % от НВ в метровом слое, продуктивность — «выше/около/ниже нормы».

**Покрытие Акмолы:** да — десятки пунктов области из 400 (38 по подстроке), районная привязка есть в объектах (`district → region`). Маппинг «станция → 10 районов Qagro» — по ближайшим координатам, ~20 строк кода.

**Оценка эффекта: СРЕДНИЙ (на доверие/риск), малый на MAE напрямую.** Исторической глубины 2005–2025 из этих ручек за час не собрать (это оперативные прогнозы/факт текущего сезона), т.е. в train-панель за час не ляжет. Зато за час ложится независимый кросс-чек: СИО-прогноз засухи vs светофор `src/risk.py`, влага %НВ vs ГТК, фенофазы календаря vs `src/recommend.py`, плюс нейтральный внешний якорь прогноза-2026. Именно этого не хватало в `EXT_SOURCES.md` (там зафиксированы только PDF-обзоры и «AgroData web» без API).

**Риск: низкий.** Только чтение, модель не трогаем; платные NDVI-тайлы не трогаем (там контракт/токен). Зависимость от неофициального API — обернуть try/except + кэш, как уже сделано для Open-Meteo.

## 2. MODIS NDVI через Open-Meteo или NASA без ключа

**Доступность: НЕТ (без ключа — нет; с бесплатным ключом — да, но не за час).**

- **Open-Meteo: вегетационного API нет.** Проверены доки `open-meteo.com/en/docs` (forecast/hourly/daily/pressure/soil caps): температура, осадки, ET0, VPD, влажность почвы, радиация — NDVI/EVI/LAI отсутствуют полностью. Живой контрольный запрос `api.open-meteo.com/v1/forecast?…` — 200, т.е. канал жив, но дать NDVI он не может в принципе.
- **NASA AppEEARS API (`appeears.earthdatacloud.nasa.gov/api/task`): 403 без токена.** MOD13Q1/MOD13C1 (NDVI/EVI 250 м–0.05°, 16-дн, 2000–н.в.) — только через Earthdata Login (регистрация бесплатная, ~10 мин) + постановка area/point-задач + ожидание выполнения. LAADS API-V2 — тоже токен. Проверено живым 403.
- Ключ-free крошка: превью NASA NEO (JPEG/PNG/GeoTIFF пережатые, ~0.1–1°) — для модели непригодно по разрешению.

**Формат (когда будет ключ):** HDF-EOS2/NetCDF/GeoTIFF через AppEEARS area-sampler по полигонам 10 районов; 16-дневные композиты, QA-биты облачности.

**Покрытие Акмолы:** полное (глобальный продукт, 2000–н.в. — в отличие от мёртвых NDVI-колонок панели, где всего 12 строк 2024 года).

**Оценка эффекта: СРЕДНИЙ (но отложенный).** Закрыл бы диагноз `MODEL_AUDIT.md §2/§4.5` (NDVI — «мёртвый груз», бэкфилл Landsat/Sentinel на train). Реалистично −0.2–0.5 MAE в засушливые годы типа 2023 + различение северного кластера (Zerenda/Burabay). Но это часы работы (задачи AppEEARS, QA-фильтр, агрегация MJJA-max), не час.

**Риск: средний.** Облачные пропуски, расхождение 250 м–1 км vs поля, конец Terra (дрейф орбиты, деградация) — для 2025+ смотреть VIIRS VNP13 как преемника. Без ключа сегодня — только зафиксировать план, не код.

## 3. data.egov.kz API — посевные площади / урожайность

**Доступность: ЧАСТИЧНО (API есть, но с ключом; агро-временных рядов урожайности нет).**

- Живая проба `GET data.egov.kz/api/v4/mapping/medorg` без ключа → **403 `{"error":"API key is required"}`**. Ключ — бесплатный из «кабинета разработчика», но требует регистрации + привязки к набору. Доки (`/pages/samples`) подтверждают схему `/api/v4/<dataset>/<version>?source={elastic-JSON}`.
- По каталогу: машиночитаемых длинных рядов урожайности/площадей по районам в открытом каталоге нет (согласуется с выводом `EXT_SOURCES.md §3`: «районных длинных рядов урожайности там нет», МСХ сводится к пресс-релизам). Есть кадастр (`land_plots` и т.п.) — не урожайность.
- **Находка рядом (не egov, но то, что реально закрывает потребность): `posev.gharysh.kz` (Қазақстан Ғарыш Сапары) — открыт без ключа.** База `/` = сезон 2024 (HTTP 200, 122 КБ, years 2018–2024 в навигации: `/2023`, `/2022`…; `/2024` отдельно даёт 404 — текущий сезон лежит на `/`). Таблица: область → район, общая посевная площадь (га), число полей, темпы сева по декадам (га + %), Акмолинская область и все её районы присутствуют (проверено наличием «Акмол» в HTML). Экспорт в Excel заявлен в шапке таблицы.

**Формат:** egov — JSON/elastic; gharysh — HTML-таблица + Excel (парсинг ~30–50 строк: итоговая площадь + число полей по району за 2018–2024).

**Покрытие Акмолы:** egov — н/а; gharysh — полное районное (все районы области, 7 сезонов).

**Оценка эффекта: СРЕДНИЙ (gharysh), малый (egov).** Районные площади 2018–2024 дополнили бы `oilseeds_share`/`grain_area_ha` (сейчас stat.gov.kz-ряд с `ffill/bfill`-оговоркой из аудита) + дали темпы сева как ранний прокси сезона-2026. На MAE — порядка −0.1–0.3 (уровень рекомендации №4 аудита), плюс досевной scope (площади известны к севу — легитимная фича без утечки, в отличие от MJJA-климата).

**Риск: низкий–средний.** gharysh — неофициальный для статистики источник (данные ДЗЗ КазEOSat), цифры могут расходиться с БНС — использовать как фичу/кросс-чек, не как якорь таргета. egov-ключ — бюрократия, выхлоп near-zero для урожайности.

**Доступность: НЕТ — подтверждено одной пробой.** Запрос к старому endpoint `cds.climate.copernicus.eu/api/v2/resources/…` → 404 с текстом «endpoint not found… update your `.cdsapirc`… `url` should be `https://cds.climate.copernicus.eu/api`, `key` = your API key». **Формат:** был бы GRIB/NetCDF, часовые/суточные агрегаты, 0.25° — но недоступен.

**Покрытие Акмолы:** нерелевантно без доступа.

**Оценка эффекта: НУЛЕВОЙ инкремент.** Даже с ключом CDS-ERA5 дублировал бы уже имеющиеся в панели Open-Meteo Archive (ERA5, CC-BY) + NASA POWER (MERRA-2). Единственный теоретический выигрыш — soil-moisture ERA5-Land 0.1° и ENSO-стрим, но soil уже проверен как null для Акмолы в Archive API (см. ## 5. Что даст больше при n≈150: isotonic-калибровка интервалов vs regime-dummy post2020 vs district-cluster фичи

Контекст из `MODEL_AUDIT.md`: главный провал — структурный разрыв масличных 2024–2025 (rapeseed bias +3.8, sunflower MAE 5.65 в 2024) + развал покрытия интервалов (flax 0.14–0.26, rapeseed 0.00 при номинале 0.80: OOF-std train занижен в ~5 раз) + геопаттерн (северный кластер Zerenda/Burabay/Sandyktau/Shortandy хуже юга).

| Метод | Стоимость (параметров при n=150/130) | Ожидаемый эффект | Риск |
|---|---|---|---|
| **regime-dummy post2020** (`post2020=(year≥2021)` + `year_trend×post2020`, `oilseeds_share×post2020`; рапсу добавить `oilseeds_share`; лаги масличных опционально дропнуть) | +2–4 коэф. на культуру — дёшево | **БОЛЬШОЙ (на MAE).** Единственный метод, бьющий в причину bias: rapeseed MAE 3.8→~1.5–2.0, sunflower 2.1→~1.2–1.5 (оценка аудита §4.1); заодно чинит ширину интервалов масличных через свежие остатки | Средний: точек нового режима мало (10–20/год) — строго train-only CV (TimeSeriesSplit), держать флаг experimental, показывать оба прогноза |
| **isotonic/режимо-взвешенная калибровка интервалов** (conformal-квантили на расширяющемся LOYO или `max(OOF_std, recent_std)`-пол; веса recent выше) | 0 новых фич, только калибровка | **БОЛЬШОЙ (на доверие), нулевой на MAE.** Покрытие 0–26%→60–80% у масличных/льна. Isotonic-регрессия именно на границах — при n=50 hold-out на культуру склонна к переобучению; audit-рецепт (§4.2: взвешенные квантили/пол) проще и честнее | Низкий (если не трогать точечный прогноз); ширина вырастет в 2–4 раза — честно, но «некрасиво» для демо |
| **district-cluster фичи** (2–3 агрозональных кластера вместо 10 one-hot: север-лесостепь vs юг-степь; или lat/lon-кластер) | +1–2 dummies — дешевле всех | **МАЛЫЙ.** Снимет часть геопаттерна (−0.1–0.2 MAE в Zerenda/Burabay), но причину (разрыв уровня + засуха-2023) не лечит; `SelectKBest` уже выкидывал lat/lon как слабые | Низкий, но и выхлоп низкий; валидировать leave-district-out |

**Ранжирование при n=150:** regime-dummy ≫ интервал-пол > isotonic-границы ≈ cluster-фичи. Причина: при n=150 каждый параметр на счету — тратить их надо на разрыв уровня (bias первого порядка), а не на тонкую геометрию остатков.
